### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

0. **Open items gate.** Before step 1, the **Before merge** list in `playbooks/opening-a-pr.md` is empty, or each item has the user's own "leave it". Side sessions you started and jobs still running count. If any item lacks an answer, ask about it now. Do not merge first and report it after.
1. **Resolve the forge, then verify each PR independently before it lands.** Read `../../principle-prove-it-works/SKILL.md` before you brief the verifiers. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One verifier per PR, each an Agent subagent in its own git worktree (`isolation: "worktree"`), runs the change the way a user would with the project's verification skill, parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would. When no CI check covers the changed code (a repo with no CI, or an app no check builds), name the check that stands in for green before you take approval. The verifier also runs the deploy target's own gate (its deploy script's tests, a dry run, or the tests on the real host) before its verdict. A gate that first fails after merge leaves code merged but not deployed. A manual deploy (copying files to a box, restarting a worker) is a landing and waits for the PR's verdict like a merge.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Land bottom-up, one PR at a time.** Always merge the run's lowest unmerged PR, with `origin pr merge <pr>` or `gh pr merge <pr> --squash`. On Origin the plain command also merges every PR below the one you name, and on GitHub a PR whose base is still its parent's branch merges into that branch, not trunk. Read the PR back for the result (`origin pr view <pr>` or `gh pr view <pr> --json state,mergedAt,baseRefName`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch. Arm `--auto` (Origin merge-when-ready or GitHub auto-merge) only on a PR whose verdict covers its current head, because it lands whatever head is ready. If the forge refuses `--auto` because auto-merge is off for the repo, and the user asked to merge on green, the merge is requested work: watch that PR's checks in the background (`gh pr checks <pr> --watch --fail-fast` with `run_in_background`) and merge when they pass. Never pass `--delete-branch` from a git worktree. It tries to switch the checkout to `main`, which another worktree holds, and errors. Merge, read the PR back, then `git push origin --delete <branch>`. After a merge lands, retarget the PR whose base was the merged branch to trunk (`origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`), move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the patch, not its commits, so step 3's patch-id rule decides whether the verdict survives. Merge it once its checks pass and its verdict survives.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. On GitHub, watch the run with the queued watcher from `playbooks/babysit.md` (`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`) under `/loop` until it reports `COMPLETE` at the ceiling. On Origin, re-read the current PR with `origin pr view <pr> --checks` each time `origin pr checks <pr> --watch` returns, until the ceiling reads merged. A base that moves to trunk when its parent merges is expected, not damage to repair. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs. End with a fixed closing block, one line each: the absolute path of the prod runbook, or `none`; the remote box or worker activation step (deploy, restart, timer enable), or `none`; the effect on existing data (old rows, threads, cached state), or `none`; open items, as `none` or each item with the user's quoted "leave it". An item first named here that the user never answered is a failure of step 0. Keep the ticket In Review while any line is not `none`. Merge-time automation marks it Done before prod is true, so move it back when it does.
