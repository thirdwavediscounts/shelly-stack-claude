### Bug fix

**You own this task. Plan, review, verify.** Delegate investigation and the fix to subagents, stay in the lead.

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix. It does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more.

1. Reproduce it yourself on the matching surface via the verification skill (Non-negotiables). Don't hand the repro to the user. You drive the instrumented runtime. Ask the user only with a stated, specific reason the verification surface cannot reach the target, and only after driving it as far as it goes. Won't reproduce directly, force it: synthesize the trigger, tighten conditions, or instrument until it fires.
   Before naming a root cause, read the fleet's real logs, not the code alone. Load deferred MCP tools with `ToolSearch` first. Query the sources for the failing surface in parallel, correlate by timestamp, and quote the log line or event as evidence.
   - **Vercel** (frontends, API routes). Vercel MCP `get_runtime_logs`, `get_runtime_errors`, and `get_deployment` build logs for the affected project and time window.
   - **Supabase** (database, RPCs, edge functions, auth). The `supabase-production` and `supabase-staging` MCPs: `query_logs` (api, postgres, edge-function, auth), `get_advisors`, and read-only `execute_sql` against the right environment. Production is read-only for diagnosis.
   - **Sentry** (frontend and backend errors). Sentry MCP `search_issues`, `search_events`, and `get_sentry_resource` for stack traces, breadcrumbs, and first-seen release.
   - **Argus Engine** (workers, scrapers, pipelines on the VPS). `ssh twd` lands as a non-root user, so use `sudo` for root-owned paths. Workers run as systemd services and timers: `systemctl list-units --type=service,timer | grep <name>`, `sudo journalctl -u <unit> --since "<time>"`, `systemctl status <unit>`. The box's code is deployed from a repo, not a live git checkout, so compare it against the repo before trusting it.
   The repro is done when you can name one command (a test, a script, a curl, a browser script) that you have already run and that meets all four checks. It drives the real code path and asserts the user's exact symptom, not "it didn't crash". It gives the same verdict every run, or for a flaky bug a pinned and high failure rate. It finishes in seconds. It runs without a human. Show the command and its redacted output. Then shrink it: cut inputs, config, data, and steps one at a time, rerun after each cut, and stop when removing anything makes it pass. No such command means no step 2. If you cannot build one, list what you tried and ask for access, a captured artifact, or permission to add temporary production logging.
2. Binary-search the cause. Call the Skill tool with `shelly-stack:how` on the affected subsystem and `shelly-stack:why` for regression history. No skip. Reading the code yourself does not replace either call. Then write three to five ranked hypotheses before testing any. Each one states its prediction: "if X is the cause, changing Y makes the bug disappear". A hypothesis without a prediction is a guess, so sharpen it or drop it. Post the ranked list to the user and keep going; they may re-rank it from what they know. Then rule them out until one survives. Each pass, take the split that cuts the most remaining problem space, get runtime evidence, eliminate. When program state is unclear, add instrumentation or logging and read it as the code runs. Change one variable per probe, and tag every debug log with one prefix such as `[DEBUG-a4f2]` so cleanup is one `grep`. Don't guess. Drive a long or stubborn hunt with Claude Code's `/loop` command. Confirm the surviving *mechanism* with runtime evidence before the step-3 architect/interrogate fan-out.
3. Plan the fix. If the change adds or changes a type, an exported signature, or a module boundary, call the Skill tool with `shelly-stack:architect` first. Otherwise mark it `skip: one function body`. Delegate implementation to a subagent using your configured bug-fix model (default `opus`) with a specific scope; review the diff. No skip at any size. Laziness Protocol does not override it, because the gain is review separation, not lines saved.
4. Verify on the same surface; the original repro now passes. Rerun the step-1 command on the original, unshrunk scenario too. `grep` the debug prefix and remove every tagged log and throwaway harness before commit. "Inconclusive" or wrong-surface is not a pass; flag it. Unit tests show branch behavior, not bug absence. When the fix claim needs a before-and-after proof, invoke **verify-this**. When the repo has a smoke suite covering the surface, invoke **run-smoke-tests**.
5. Stage the commits so the failing repro lands before the fix in git history. See the **tdd** skill for the failing-test-first cadence when the bug has a cheap local test path. Skip it when the test would be expensive, integration-heavy, or unclear. Write a regression test only at a seam that reproduces the real bug pattern. When the only seam is too shallow to catch it, say so in the PR as a finding instead of adding a test that gives false confidence. Name the hypothesis that held in the commit body.
   This follows `../../principle-sequence-verifiable-units/SKILL.md`, the failing test first and the fix on top.
6. Run **Opening a PR**.

Investigation fans out `how` + `why` as parallel subagents.

**Reply:** what was broken, the ranked hypotheses and which one held, root cause, fix, how you verified. Paste failing-then-passing repro output verbatim.
